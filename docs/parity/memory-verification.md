# Memory, baking and full-resolution evidence

## Production changes

- Deleted RAM/VRAM admission APIs and their callers in mesh maps, height/displacement, texture/UDIM decoding, export, material metadata and SPSM parsing. Removed configured memory preferences, environment overrides and inert decoder/parser budget members. Actual available RAM and GPU-owner VRAM telemetry have no 50% factor. Structural overflow, invalid dimensions/indexes, corrupt-file checks, UINT32 archive representation bounds, actual stack safety and per-frame work quotas remain.
- Texture residency preserves project dimensions. Cache eviction uses actual free bytes plus reusable owned storage, including known-zero VRAM. Filled-path, ribbon and clone/smudge caches evict disposable entries before actual driver allocation; exhausted eviction no longer causes a preflight refusal. No automatic resolution substitution or “full resolution retained” message remains.
- Baking runs sequentially by Texture Set, UDIM and map. AO/thickness dispatch only the current map through a GPU-owner mailbox. Each production dialog request refreshes actual free VRAM, batches within available memory and driver limits, and releases GPU scratch afterward. Failed GPU preparation continues with the existing CPU implementation. Object-specific ray filters retain their CPU semantics. Pending cancellation wakes and clears the request before destructor join; cancellation cannot lose its condition-variable notification.
- Full-resolution surface atlases, native raster buffers and high-poly tangent scratch use file-backed vectors. Linux reserves disk extents before mapping; copies own independent mappings and moves transfer ownership. The OS pages these buffers according to actual memory pressure. Completed mesh maps use existing immutable disk-backed storage; no eager GPU preparation retains every map or Texture Set.
- Bake entry suspends viewport painting with cancellation/error-safe restoration, retires recomputable stack-prefix/mask/input caches, finishes GPU work and refreshes VRAM. Authored adjustment owners and leased native resources remain alive.

## VRAM investigation

GpuLayerPreview retains full-resolution intermediate prefix images by channel, layer stack and UDIM, plus source-image caches. RGBA32F storage is 256 MiB per 4K image or 1 GiB per 8K image, so multiple prefixes intentionally retain gigabytes. This inspection does not prove a leak in the original reported 14.5 GB session; that project/session was not reproduced.

A five-layer 1024² fixture was rendered, reclaimed and rebuilt three times. Every release accounted for 33,554,496 bytes; driver free VRAM rose by 34 MiB and returned to the identical 19,432,256 KiB baseline each cycle. Every rebuilt composite had SHA256 `022a6d8291af6c33370033c2683b6fb204ec61a5010a428ede404677f3e0977a`. Authored paint and COW snapshots stayed exact. An immediate second release returned zero. No cumulative growth occurred in this fixture. Blender's texture tracker reported zero on this build, so driver counters and owned-resource accounting are the valid telemetry.
